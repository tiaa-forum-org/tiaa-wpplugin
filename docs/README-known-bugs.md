### Known bugs or incomplete investigations
#### 1. ~~Problem with saving options as an array~~ — RESOLVED 2026-08-20
`WelcomeSettings.php` used `validate_options` instead of `validate_options_blank_ok`, forcing
Discourse URL/API key/username to be re-entered on the Welcome tab instead of falling back to
the Connection tab like Invite and Group Invite do.

Root cause turned out to be two separate bugs, not the array-coercion issue originally suspected:
1. `validate_options_blank_ok` — the method `InviteSettings.php`/`GroupInviteSettings.php` already
   passed to `register_setting()` — didn't exist anywhere in the codebase. WP's `register_setting()`
   only attaches a sanitize callback when `is_callable()` is true, so it silently skipped validation
   entirely for those two tabs; that's why blank worked for them (no validator ran at all, not a
   working blank-tolerant one).
2. A naming mismatch (`tiaa_validate_api_blank_ok` instead of `tiaa_validate_api_key_blank_ok`) meant
   even a correct dispatcher would have missed the API key's blank-ok filter.

Fixed: added a real `FormHelper::validate_options_blank_ok()` that dispatches each field through its
`tiaa_validate_{key}_blank_ok` filter when one is registered, falling back to the strict
`tiaa_validate_{key}` filter otherwise (e.g. `cron_interval`); fixed the api_key filter name; pointed
`WelcomeSettings.php` at the new method. Verified directly: blank url/api_key/username now save with
no settings errors, `group_list` still comes back as an array (not coerced to a string), and non-blank
invalid input (bad URL, bad API key format) still errors as before.

#### 2. ~~Logger handling~~ — RESOLVED 2026-08-19
`TIAAFile.php` was buried in the `\Analog` (`vendor_prefixed/`) area, which risked silent
deletion if that tree were ever regenerated by the php-prefixer tool, since it's TIAA-specific
code that never actually went through that tool and doesn't exist in the upstream
`analog/analog` package.

Fixed via refactor: moved `TIAAFile.php` from `vendor_prefixed/` into `lib/`, the actual plugin
library, keeping its `TIAAPlugin\Analog\Handler` namespace for a minimal diff (no call-site
changes needed beyond the `require_once` path in `vendor_prefixed/autoload.php`). See
`CLAUDE.md`'s Deployment/Known Issues history for the fuller writeup of that move.

#### 3. ~~Group invite case-sensitivity~~ — RESOLVED 2026-08-21
A post that should have been readable via the API appeared to fail specifically for the
Archives group invite, with the invite seeming to not come from the assigned credentials --
initially looked like a credentials/access problem, especially since the admin "Get Message"
test button worked fine while the real invite send didn't.

Root cause turned out to be unrelated to credentials or post access entirely:
`OptionsUtilities::options_init()` builds each group's option-group key
(`tiaa_group-invite-{name}`) using the exact casing typed into the free-text "List of Groups"
admin field (`group_list`). `TiaaHooks::invite_to_discourse()` was building its own lookup key
directly from the *submitted form's* `group` value, with no validation that the two matched.
Any casing drift between the form, `group_list`, and Discourse's own case-sensitive group slug
caused the option lookup to silently miss the already-correctly-configured entry, failing the
entire invite outright with an opaque `"No options"` 500 error -- not a partial/wrong-sender
send. Confirmed by deliberately mismatching `group_list`'s casing against a real invite
submission and reproducing the exact error, then reverting.

A secondary contributor: `Discourse::get_discourse_post_by_id()` swallowed this same failure
with **no logging at all** (unlike `TiaaHooks::invite_to_discourse()`'s own credential check,
which does log), making the failure look intermittent/silent depending on which code path hit
the mismatch first.

Fixed: added `PluginUtil::resolve_configured_group_name()`, which resolves a submitted group
name against `group_list` case-insensitively and returns the exact configured casing --
`TiaaHooks::invite_to_discourse()` now uses that resolved name for both the WP option lookup
and Discourse's `group_names` param (also case-sensitive there), and returns a clear
`unknown_group` 400 instead of an opaque 500 if no match exists. Also added the missing log
call in `get_discourse_post_by_id()`. Verified directly: a mismatched-case form submission
against the current, correctly-configured `group_list` now succeeds and correctly attaches the
"Archives" group to the created invite; a genuinely unrecognized group now returns a clear
400 error instead of a 500.
